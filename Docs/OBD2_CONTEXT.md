# Контекст: чтение данных автомобиля через OBD2-адаптер

Документ собирает контекст для реализации v2: как устроена связь с адаптером, что умел легаси-код (LTBLT), что такое стандартный OBD-II, что такое «профиль» и как всё это ложится на данные, собранные командой (PDF «OBD-II (vol. 2) — Coverage»).

---

## 1. Что было в v1 — легаси LTBLT

Группа `OBD2Scanner/Classes/LTBLT` — это библиотека **LTSupportAutomotive** (Dr. Michael Lauer, github.com/mickeyl/LTSupportAutomotive), Objective-C, скопированная в проект. Поверх неё — тонкая Swift-обёртка `Classes/Service/OBDAdapter/OBDAdapter.swift`.

### Архитектура (снизу вверх)

1. **`LTBTLESerialTransporter`** — BLE-транспорт. CoreBluetooth central: сканирует эфир (без фильтра по сервисам — «some devices are not advertising the service ID»), подключается к первому устройству, у которого находит characteristic с `notify` (чтение) и с `write` (запись), оборачивает их в пару `NSInputStream`/`NSOutputStream`. Известные сервисы BLE-адаптеров, которые передавала обёртка: `FFF0`, `FFE0`, `BEEF`, `E7810A71-73AE-499D-8C15-FAA9AEF0C3F2`.
2. **`LTOBD2Adapter` / `LTOBD2AdapterELM327`** — сессия с ELM327-чипом. Инициализация: `ATD → ATZ → ATE0 → ATL0 → ATS1 → ATRV → ATSP0 → ATH1 → ATI → ATS0`, затем проверка связи с машиной через `0100` и определение протокола `ATDPN`; если авто-режим не сработал — перебор протоколов `ATTP1..9`. Ответы парсятся по терминатору `>`, мусорные байты клонов фильтруются.
3. **`LTOBD2Protocol*`** — разбор кадров ответа по протоколам: ISO 15765-4 (CAN 11/29 бит, сборка multi-frame по PCI-байту, группировка ответа по ECU-адресу), ISO 9141-2, ISO 14230-4 (KWP2000), SAE J1850.
4. **`LTOBD2Command` / `LTOBD2PID`** — команда = сырая hex-строка запроса + парсер ответа. На каждый PID — отдельный Obj-C класс (`LTOBD2PID_ENGINE_RPM_0C` и т.д., ~900 строк заголовка).

### Что библиотека умела

- **Mode 01** — live data: ~50 классов PID (нагрузка, температуры, обороты, скорость, топливные тримы, лямбды, катализатор, дроссель и т.д.), плюс проверка поддержки через bitmap-PID (`LTOBD2PID_TEST_SUPPORTED_COMMANDS`, `LTOBD2PIDDB`).
- **Mode 02** — freeze frame: инфраструктура была (`pidForFreezeFrameDTC:`, `LTOBD2PID_DTC_CAUSING_FREEZE_FRAME_02`), любой mode-01 PID можно было запросить из кадра.
- **Mode 03 / 07 / 0A** — stored / pending / permanent DTC, **Mode 04** — очистка.
- **Mode 06** — результаты мониторингов, **Mode 09** — VIN, Calibration ID, ECU name.
- AT-команды: напряжение АКБ (`ATRV`), зажигание (`ATIGN`), описание протокола.

### Что реально использовало приложение

`OBDAdapter.swift`: подключение, mode 03 DTC (`obtainDTC`), три сенсора для дашборда (RPM/скорость/температура ОЖ через `readSensorData`) и плоский список ~70 PID для экрана PIDs. Freeze frame, mode 06/07/0A, выбор ECU — не использовались. ViewModels (DTC, PIDs) сейчас закомментированы.

### Почему «данных было мало» — главный вывод

1. **Только стандартный SAE J1979.** Машина отдаёт лишь те PID, которые декларирует в битмасках (`0100`, `0120`, …) — на практике это 20–60 эмиссионных параметров двигателя. Температуры масла/АКПП, DPF, давление наддува по маркам, состояние батареи EV и т.п. живут в **производительских** протоколах, которых в v1 не было вообще.
2. **Только functional-запросы «всем ECU»** (0x7DF). Адресация конкретных блоков (ABS, коробка, кузов, приборка) не использовалась — а без неё бо́льшая часть машины невидима.
3. Технические слабости: подключение к первому попавшемуся BLE-устройству; нет нормальных таймаутов/ретраев; последовательный опрос PID по одному → низкая частота обновления; capriзные клоны ELM327 (v1.5 официально не существует — это маркер клона; `ATIGN` у клонов часто нет, в коде это уже было закомментировано).

Легаси подтверждает: транспорт и ELM327-слой концептуально правильные, ограничение — в **отсутствии производительского уровня** и в подходе «класс на PID», который не масштабируется.

## 2. Как устроена связь через OBD2-адаптер

```
Приложение ⇄ BLE/Wi-Fi/BT ⇄ ELM327 (или клон / STN) ⇄ шина авто (CAN / K-line) ⇄ ECU
```

- **ELM327 — «модем» с текстовым интерфейсом.** Строки, начинающиеся с `AT`, — команды самому адаптеру. Всё остальное трактуется как hex-байты и отправляется в шину. Ответ — hex-строки (с CAN-заголовками при `ATH1`), терминатор — символ `>`.
- **Протоколы шины** (`ATSP0` — автоопределение; номер по `ATDPN`): `1/2` — SAE J1850 PWM/VPW (старые американцы), `3` — ISO 9141-2, `4/5` — ISO 14230-4 KWP2000 (K-line), `6–9` — **ISO 15765-4 CAN** (11/29 бит × 500/250 кбит). Все автомобили примерно с 2008 года (США) и практически весь охват из PDF — это CAN 11 бит 500 кбит (протокол 6).
- **ISO-TP (ISO 15765-2)** — транспортный слой поверх CAN: кадр 8 байт; single frame несёт ≤7 байт данных, длинные ответы идут multi-frame (First Frame → Flow Control → Consecutive Frames). ELM327 сам собирает входящие multi-frame и сам отвечает Flow Control. **Отправлять** запросы длиннее 7 байт данных стандартный ELM327 не умеет — для чтения данных это почти никогда не мешает (запросы короткие), полноценно решается только чипами STN (OBDLink).
- **Адресация.** Functional-запрос `0x7DF` — «всем эмиссионным ECU», отвечают `0x7E8–0x7EF` (двигатель почти всегда `0x7E8`, ответный ID = запросный + 8). Physical-запрос — конкретному блоку: `ATSH 7E0` (кому шлём) + `ATCRA 7E8` (чей ответ принимаем). Блоки за пределами эмиссионных имеют свои пары ID — например, у VAG шлюз, приборка, ABS и т.д. имеют собственные request/response CAN ID (репозиторий `vag-uds-ids` — как раз такая карта, извлечённая из ODIS).
- **Ключевые AT для производительского уровня:** `ATSH` (заголовок запроса), `ATCRA` (фильтр приёма), `ATFCSH`/`ATFCSD` (кастомный flow control), `ATCAF0/1` (ручной/авто ISO-TP), `ATST`/`ATAT` (таймауты), суффикс числа ожидаемых ответов (`010C 1` — не ждать таймаут, зная, что ответ один; главный буст частоты live data).

## 3. Базовый уровень: стандартный OBD-II (SAE J1979)

Обязателен для бензина с 1996 (США) / 2001 (ЕС), дизеля — с 2004 (ЕС). Работает одинаково на всех марках — это и есть «профиль по умолчанию», fallback.

| Сервис (mode) | Что делает |
|---|---|
| `01` | Текущие данные (live data) по PID |
| `02` | Freeze frame — те же PID из зафиксированного кадра |
| `03` | Stored DTC (подтверждённые, MIL горит) |
| `04` | Очистка DTC и стёртых значений |
| `06` | Результаты бортовых мониторингов (test results) |
| `07` | Pending DTC (не подтверждённые) |
| `09` | Информация об авто: VIN (`0902`), Calibration ID и др. |
| `0A` | Permanent DTC (не стираются командой 04) |

- **Live data:** запрос `010C` → ответ `41 0C A B` → RPM = (256·A+B)/4. Формулы стандартизованы (SAE J1979 / таблица в Wikipedia «OBD-II PIDs»). Поддержка объявляется битмасками `0100` → PID 01–20, `0120` → 21–40 и т.д. На CAN можно запрашивать до 6 PID одним запросом (`01 0C 0D 05`) — поддерживается не всеми ECU, нужен fallback.
- **DTC (mode 03):** ответ `43 …`, по 2 байта на код. Старшие 2 бита первого байта → буква: `00`=P, `01`=C, `10`=B, `11`=U; дальше цифры из ниблов. На CAN первый байт ответа — количество кодов (легаси это учитывал — `LTOBD2PIDStoredDTC`). Расшифровки P0xxx-кодов стандартны; P1xxx/P3xxx — производительские, нужна своя база описаний.
- **Freeze frame (mode 02):** сначала `0202 00` — какой DTC вызвал фиксацию кадра 00, затем `02 <PID> 00` — любые PID из кадра. Битмаска поддержки — `0200 00`. Кадров может быть несколько (00, 01, …).

Ограничение уровня: только выхлоп/двигатель, только то, что производитель обязан отдать. Именно поэтому v1 показывала мало.

## 4. Что такое «профиль», почему они разные и как их использовать

**Профиль = полное описание того, как разговаривать с конкретным семейством ECU конкретного производителя, чтобы достать данные сверх стандарта.** Стандартизован только эмиссионный минимум; всё остальное каждый производитель делает по-своему, поверх своих диагностических протоколов:

- **UDS (ISO 14229)** — современный стандарт «формы», но не «содержания»: сервисы одинаковые, а идентификаторы данных и формулы у каждого свои. Практически всё с ~2008–2012+ (весь MQB, Stellantis EMP2/CMP, TNGA, CLAR, MRA и т.д. из PDF).
- **KWP2000 (ISO 14230)** — предыдущее поколение; сервис `21` ReadDataByLocalIdentifier. Denso (Toyota) и Keihin (Honda) во многом сохранили «стиль 21» даже на новых машинах.
- **KWP1281, TP2.0** — старый VAG (до ~2008, K-line и CAN соответственно). На ELM327 TP2.0 практически нереализуем (подтверждено опытом vag-blocks) — этот сегмент разумно оставить за скоупом.

Разность профилей — прямое следствие того, что ПО для ECU пишут разные поставщики (Bosch, Continental, Delphi, Denso, Kefico, Keihin/Hitachi…), и даже внутри одной марки бензиновый ECU, дизельный ECU и коробка (например, DSG DQ381) — это разные семейства с разными таблицами данных. Отсюда в PDF «несколько профилей на одну модель».

### Из чего состоит профиль (минимальный состав)

1. **Протокол/транспорт:** CAN 11/29 бит, скорость (почти всегда `ATSP6`).
2. **Карта адресов:** request/response CAN ID каждого интересующего ECU (двигатель, коробка, ABS, приборка…). Пример: VAG engine = `7E0/7E8`.
3. **Инициализация сессии:** UDS `10 03` (extended session), если требуется; периодический tester present `3E 80`, чтобы сессия не отваливалась. Security access (`27`) для **чтения** обычно не нужен.
4. **Таблица параметров — сердце профиля:** список DID (16-битные идентификаторы для UDS `22` ReadDataByIdentifier) или local id (для KWP `21`), и для каждого — имя, формула (offset/factor/битовые поля), единицы, минимум/максимум. Пример: `22 F4 0C` — у многих Bosch-ECU обороты; `22 2E 97` — температура масла на части VAG и т.п. (конкретные DID — предмет сбора по каждому семейству).
5. **Чтение DTC по-производительски:** UDS `19 02 <statusMask>` (обычно `0x8F`/`0xFF`) — коды **3-байтные** + байт статуса (не как в J1979!); расшифровка тоже своя.
6. **Freeze frame по-производительски:** UDS `19 04` (snapshot record по конкретному DTC) — там данных сильно больше, чем в mode 02.

### Как профиль используется в рантайме

```
1. Подключились к адаптеру, инициализировали ELM327 (как в легаси)
2. Определили автомобиль: VIN (0902) → марка/платформа/двигатель
   (в приложении уже есть Garage + VIN decode — выбор профиля отсюда)
3. Всегда: базовый J1979 (работает на всём)
4. Если есть профиль: ATSH/ATCRA на нужный ECU → 10 03 → опрос DID из таблицы,
   19 02 для DTC, 19 04 для snapshot; периодически 3E 80
5. Профиль не сработал (нет ответа/NRC) → graceful fallback на J1979
```

Отрицательный ответ UDS: `7F <sid> <NRC>` (например, `7F 22 31` — requestOutOfRange: DID не поддерживается). Это штатный механизм проверки «поддерживается ли параметр» — аналог битмасок J1979: пробуем DID, `7F` → выкидываем из списка.

### Питон команды

Коллеги, получающие данные python-скриптами, почти наверняка используют python-OBD (J1979) и/или udsoncan + isotp (mode 22). **Их рабочие скрипты — самый ценный артефакт:** из них извлекаются проверенные последовательности байт (адреса, сессии, DID, формулы), которые переносятся в профили приложения 1:1 — транспорт у нас тот же ELM327.

## 5. Разбор PDF «Coverage» и ссылок команды

Таблица — это **карта покрытия** (какие профили собирать), а не сами данные: Группа → Платформа → Тип (бензин/дизель/коробка/EV) → семейство ECU → модели. Итог по PDF: ~11 групп, ~30 платформ, ~100 ECU-профилей.

Замечания по строкам:

- **VW Group (MQB/MEB/MLB)** — UDS, лучший в индустрии community-контент (ODIS/VCDS-наследие). Самый благодарный первый профиль.
- **Toyota/Lexus (Denso)** — специфика: многое через сервис `21` (KWP-стиль) даже на TNGA; «по номеру детали» в PDF — верное наблюдение: таблицы зависят от партномера ECU.
- **Tesla** — на Model 3/Y классического J1979 нет; данные берут пассивным чтением шины через спец-переходник, сигналы известны из opendbc. Это отдельный тип «профиля» (broadcast-сниффинг `ATMA`, а не запрос-ответ) — стоит решить, в скоупе ли он вообще.
- **Старый VAG / TP2.0** — вне разумного скоупа для ELM327 (см. vag-blocks).

## 6. Следствия для архитектуры v2

> Конкретный формат профиля (JSON-схема, примеры, устройство движка) — в отдельном документе: `Docs/OBD2_PROFILE_FORMAT.md`.

- **Слои:** Transport (BLE, позже Wi-Fi) → AdapterSession (init ELM327, очередь команд, таймауты/ретраи, работа с клонами) → Codec (J1979 + UDS/KWP: сборка запроса, разбор ответа, NRC) → **ProfileRegistry** → Features (LiveData-поллер, DTC, FreezeFrame).
- **Профиль — это данные, а не код.** Легаси-подход «Obj-C класс на каждый PID» на ~100 профилей × десятки DID не масштабируется. Профиль = декларативное описание (JSON/plist): адреса, init-последовательность, DID → формула → единицы. Тогда профили можно поставлять с сервера без релиза.
- **Fallback всегда:** J1979 — базовый уровень для любой машины; профиль только добавляет сверху; любой сбой профиля деградирует в базу, а не в ошибку.
- **Терминология:** в проекте уже есть `ProfileManager` (профиль пользователя, серверный). Для ECU-профилей использовать другое имя — например `VehicleProfile`/`DiagProfile` — чтобы не путаться.

## 7. Сверка со скриптами команды (08.07.2026)

Команда прислала 5 python-скриптов (python-obd, Wi-Fi ELM327 v1.5, машины: Citroen C5 2004 и Peugeot 407 2007). Главный факт: **все скрипты работают только со стандартным SAE J1979** — производительских протоколов (UDS/mode 22) они не касаются. То есть скрипты проверяли ровно тот слой, который в приложении реализует `obd2-standard.json`.

| Скрипты делали | В ядре приложения |
|---|---|
| Подключение к ELM327, автоопределение протокола, ручное форсирование | `ELM327Session` (init-последовательность) + движок: `ATSP<из профиля>` → fallback `ATSP0`, `ATDPN` |
| `supported_commands` — что поддерживает машина | Тот же механизм: битмаски `0100/0120/…` (`probeJ1979Page`) |
| Цикличное чтение живых параметров (mode 01) | Поллер live-fast/live-slow + `OBDService.liveData()` |
| Заводской freeze frame (mode 02, `DTC_*` команды) | `readFreezeFrame` для J1979-кодов (mode 02) |
| Напряжение адаптера (`ELM_VOLTAGE`) | `readVoltage()` (`ATRV`) |
| «Свой снимок» — прочитать всё разом и сохранить | Фича уровня приложения поверх `liveData()` (сохранение — TODO UI) |

Что в ядре есть **сверх** скриптов: производительские профили (UDS-сессии, DID, snapshot 19 04), DTC с ECU-адресом и происхождением, подбор профиля по авто, multi-ECU.

Зафиксированные пробелы относительно скриптов:
1. **Wi-Fi транспорт** — скрипты работают через Wi-Fi-адаптеры (`socket://192.168.0.10:35000`); в v1 приложения только BLE (решение продукта). Добавляется одним классом `WiFiTransport` за интерфейсом `OBDTransport`.
2. ~~Полнота таблицы PID~~ — **закрыто 08.07.2026**: в `obd2-standard.json` портирована полная таблица mode-01 PID SAE J1979 (паритет с python-obd).
3. **Не-CAN машины** (C5 2004 — K-line): у нас best-effort путь (ATH0 + склейка), python-obd разбирает старые протоколы полноценнее. Для машин 2008+ (весь охват PDF) разницы нет — там CAN.
4. **Вычисляемые параметры** (скрипт считает мгновенный расход из MAF: `MAF/14.7/745×3600` л/ч, ÷скорость×100 → л/100км) — слой поверх readings, в ядре не реализован; хорошая идея для продукта.

**Откуда берутся данные для профилей (важно не путать):**
- Стандартные PID (mode 01/02) — из **стандарта SAE J1979**; это фиксированная публичная таблица (она же зашита в python-obd). GitHub-репозитории для неё не нужны.
- Производительские DID (mode 22) — вот для них нужны материалы из репозиториев и находки команды: адресация блоков (vag-uds-ids), таблицы параметров и формулы (community-базы, VCDS label-файлы), уроки (vag-blocks: TP2.0 на ELM нестабилен).

# Формат ECU-профиля (v1, черновик)

Ответ на вопрос «как профили выглядят и что из себя представляют». Профиль — это **JSON-документ с данными, а не код**. В приложении живёт один универсальный движок-интерпретатор, который умеет исполнить любой профиль: открыть сессию с нужным ECU, опросить параметры, прочитать DTC и freeze frame, расшифровать байты по описанным формулам. Новая машина = новый JSON, без изменения кода. Сначала JSON лежат в бандле, позже те же файлы отдаёт сервер.

Ключевая идея: **стандартный OBD-II (SAE J1979) — это тоже профиль в этом же формате** (`obd2-standard.json`). Он работает на любой машине и всегда включён как база; производительские профили добавляют данные поверх него. Движок один, форматов не два.

---

## 1. Структура профиля

```json
{
  "schemaVersion": 1,
  "id": "vag-mqb-petrol",
  "name": "VW Group MQB — бензин (Bosch MED17 / MG1)",
  "priority": 100,

  "match": {
    "brands": ["volkswagen", "skoda", "seat", "audi", "cupra"],
    "years": { "from": 2013 },
    "vinWMI": ["WVW", "WVG", "TMB", "VSS", "WAU"]
  },

  "bus": { "elmProtocol": "6" },

  "ecus": [ /* см. ниже */ ]
}
```

| Поле | Смысл |
|---|---|
| `schemaVersion` | Версия схемы. Движок отказывается исполнять незнакомую версию (важно для будущей серверной доставки) |
| `id` | Уникальный идентификатор профиля |
| `priority` | Если авто подходит под несколько профилей — берётся более специфичный (больший приоритет) |
| `match` | Критерии подбора: `brands`, `models`, `years` из Garage, `vinWMI` — первые 3 символа VIN. Все поля опциональны, работают как AND. Для платформенных профилей (разные ECU-таблицы у моделей одной марки) обязательно сужать через `models`. **`fuelTypes` пока не использовать:** в приложении нет источника типа топлива (в `Vehicle` поля нет), профиль с этим критерием молча никогда не подберётся — подключим после появления определения топлива (VIN-декод или PID 0151) |
| `bus.elmProtocol` | Номер протокола ELM327 (`6` = CAN 11 бит 500k — почти всегда; `3` = ISO 9141-2 K-line на машинах до ~2006, напр. Honda S2000). Движок делает `ATSP6` вместо автоопределения — быстрее и надёжнее |

**Не-CAN шины (K-line ISO 9141-2 / KWP, J1850).** Производительские ECU-каналы на них не поднимаются (нет ISO-TP и CAN-адресации), но профиль всё равно полезен как подсказка протокола — `honda-s2000` ровно такой: `elmProtocol: "3"` и пустой `ecus`, данные идут через стандартный профиль. Контракт движка на не-CAN: команды адресации (`ATSH`/`ATCRA`/фильтры) не шлются вовсе — у ELM327 байты заголовка общие для всех протоколов, и CAN-адрес `7DF` сломал бы K-line заголовок (`00 07 DF` вместо `68 6A F1`, ECU замолкает); заголовки ответа выключаются (`ATH0`), и каждая строка ответа разбирается как отдельное сообщение — склейка недопустима (эхо сервиса второго ECU попадает в данные первого и рождает фантомные DTC); потолок ожидания поднимается (`ATSTFF`, ~1 с) — шина работает на 10.4 kbps; multi-message ответы (VIN `49 02 <номер> <4 байта>`) складываются по номеру сообщения на уровне читателя.

## 2. Секция ECU

Один профиль описывает несколько блоков (двигатель, коробка, ABS…). Каждый — со своей адресацией и сессией:

```json
{
  "id": "engine",
  "name": "Двигатель",
  "addressing": { "request": "7E0", "response": "7E8" },

  "session": {
    "kind": "uds",
    "open": ["1003"],
    "testerPresent": { "request": "3E80", "intervalSec": 2 }
  },

  "dtc": {
    "read":        { "request": "1902AF", "format": "uds" },
    "clear":       { "request": "14FFFFFF" },
    "clearSingle": { "request": "14{dtc}" },
    "freezeFrame": { "request": "1904{dtc}FF", "format": "udsSnapshot" }
  },

  "parameters": [ /* см. ниже */ ]
}
```

- **`addressing`** — движок перед работой с ECU выставляет `ATSH 7E0` + `ATCRA 7E8`. Функциональная адресация (для стандартного профиля) — `"request": "7DF"`, без `ATCRA`.
- **`session.open`** — последовательность запросов для открытия сессии (UDS `10 03` = extended diagnostic session). Для стандартного OBD-II сессия не нужна: `"kind": "none"`.
- **`testerPresent`** — движок шлёт `3E 80` каждые N секунд, пока ECU активен, иначе extended-сессия закрывается сама.
- **`dtc.read`** — UDS: `19 02 AF` (reportDTCByStatusMask; маска AF = confirmed+pending+…). `format: "uds"` говорит парсеру: в ответе `59 02 <availabilityMask>` дальше идут записи по 4 байта — 3 байта кода + 1 байт статуса. Формат J1979 (`format: "j1979"`) — 2 байта на код, ответ `43 …`.
- **Контракт разбора DTC (зафиксирован в кодеке, `DTCDecoder.decode`):** эхо позитивного ответа выводится из запроса — первый байт + 0x40 (`03`→`43`, `19`→`59`). Для `j1979` кодек снимает 1 байт эха; на CAN-протоколах (ELM 6–9) следующий байт — счётчик кодов, тоже снимается (на K-line счётчика нет — решает флаг протокола). Для `uds` снимаются 3 байта: эхо `59`, эхо подфункции и availabilityMask. Происхождение кода: запрос `03` → stored, `07` → pending, `0A` → permanent; для UDS — из байта статуса (бит confirmedDTC `0x08` → stored, иначе pending). Каждому коду кодек приписывает адрес ECU-источника — при broadcast-запросе коды разных блоков различимы.
- **`dtc.clear`** — полный сброс кодов блока: J1979 mode `04` или UDS `14 FFFFFF` (clearDiagnosticInformation, группа `FFFFFF` = «все DTC»). Подтверждение — позитивное эхо (`44` / `54`); движок считает сброс успешным, если эхо пришло хотя бы от одного ECU (при broadcast mode 04 часть блоков штатно молчит). Вместе с кодами ECU стирает freeze frame и статусы мониторингов, MIL гаснет. Permanent-коды (mode 0A) командой не стираются — гаснут сами после успешных циклов мониторинга. Точечного сброса в J1979 нет: mode 04 параметров не принимает.
- **`dtc.clearSingle`** — точечный сброс одного кода, только UDS: `14 <DTC:3 байта>` (`{dtc}` — плейсхолдер, движок подставляет `DiagnosticTroubleCode.raw`). Запрос уходит тому ECU, который код сообщил. Поддержка опциональна по ISO 14229 — на NRC `0x11/0x12/0x31` движок возвращает `.clearNotSupported`, и UI предлагает полный сброс.
- **`dtc.freezeFrame`** — UDS `19 04 <DTC:3 байта> FF` (reportDTCSnapshotRecordByDTCNumber). `{dtc}` — плейсхолдер, движок подставляет 3 сырых байта кода (они хранятся в `DiagnosticTroubleCode.raw`). Данные внутри snapshot лежат списком `DID → байты`, но длина данных каждого DID в ответе **не кодируется** (ISO 14229) — `UDSSnapshotParser` берёт длины из таблицы `parameters` (поле `dataLength`, по умолчанию `extract.start + extract.length`) и **останавливается на первом неизвестном DID**, помечая результат `isTruncated`. Показываем всё, что описано профилем, и не гадаем на остальном. Значения известных DID расшифровываются той же таблицей `parameters`.

## 3. Параметры — сердце профиля

```json
{
  "id": "engine.rpm",
  "name": "Обороты двигателя",
  "request": "22F40C",
  "responsePrefix": "62F40C",
  "extract": { "start": 0, "length": 2 },
  "decode": { "kind": "linear", "scale": 0.25, "offset": 0 },
  "unit": "rpm",
  "range": { "min": 0, "max": 8000 },
  "group": "live-fast",
  "categories": ["engine", "hud"]
}
```

| Поле | Смысл |
|---|---|
| `request` | Сырая hex-строка запроса. UDS: `22` + DID (`F40C`). J1979: `010C`. KWP: `21` + local id. Движку всё равно — он шлёт строку |
| `responsePrefix` | Ожидаемое начало позитивного ответа (`62` = `22`+0x40, эхо DID). Всё после префикса — данные |
| `extract` | Какие байты данных взять: смещение и длина. Опционально `signed: true`, `endian: "little"` (по умолчанию unsigned, big) |
| `dataLength` | Полная длина данных DID в байтах — для разбора UDS snapshot, где длина в ответе не кодируется. По умолчанию `extract.start + extract.length` |
| `decode` | Как превратить целое в значение (см. ниже) |
| `group` | Группа опроса: `live-fast` (HUD, крутим постоянно), `live-slow` (раз в несколько секунд), `once` (VIN и константы) |
| `categories` | Теги для UI (какие параметры показывать на приборной панели, какие в списке) |
| `range` | Ожидаемый физический диапазон. Движок помечает значения вне диапазона как недостоверные в отчёте самопроверки (`LiveSessionReport`) |
| `crossCheck` | Самопроверка: опорный параметр, с которым значение должно сходиться на живой машине (см. ниже) |

### Самопроверка: `crossCheck`

```json
{ "crossCheck": { "reference": "std.rpm", "relative": 0.2, "absolute": 100 } }
```

Опора (`reference`) — id параметра, обычно из `obd2-standard`: стандартные PID
машина отдаёт по спецификации, им можно верить. Значение достоверно, если
`|значение − опора| ≤ max(absolute, relative × |опора|)`; допуски опциональны
(по умолчанию `relative` 0.2, `absolute` 5). Во время live-опроса движок
(`LiveSessionAuditor`) сверяет каждое значение со свежей опорой (окно 30 с)
и после остановки отдаёт `LiveSessionReport`: что молчит, что вне `range`,
что разошлось с опорой. Отчёт `Codable` — сегодня печатается в лог тестового
экрана, позже той же схемой уедет в аналитику/на сервер.

Зачем: раскладки в community-базах (OBDb и т.п.) местами сняты с другого
поколения — сдвиг на байт даёт «правдоподобный мусор». Живой тест Camry
11.07.2026: сдвинутый блок `2101` дал 57347 rpm и −30 °C — диапазон и сверка
ловят такое автоматически, глазами вычитывать 300 параметров не нужно.

### Виды `decode`

Проверка по легаси-коду и таблицам J1979: этих видов хватает на ~всё, что мы встречали:

```json
{ "kind": "linear", "scale": 0.75, "offset": -48 }
```
`value = raw × scale + offset` — покрывает ~90% параметров (RPM: ×0.25; температуры: −40; тримы: ×(100/128)−100 и т.д.).

```json
{ "kind": "enum", "map": { "1": "Open loop", "2": "Closed loop", "4": "Open loop (нагрузка)" } }
```
Статусы, типы топлива, режимы.

```json
{ "kind": "bitfield", "flags": [ { "bit": 7, "name": "MIL горит" } ] }
```
Битовые маски (статусы мониторингов и т.п.). Номер бита — абсолютный, от младшего бита целого, собранного из всех байт `extract`.

```json
{ "kind": "ascii" }
```
VIN, номера прошивок. Непечатаемые байты (паддинг `0x00`/`0xFF` — обычное дело в ответах ECU) отбрасываются, остаётся только ASCII `0x20–0x7E`.

Один запрос может отдавать несколько величин (например, лямбда: напряжение + трим в одном ответе) — это просто **несколько параметров с одинаковым `request` и разными `extract`**; движок дедуплицирует одинаковые запросы в цикле опроса.

Если позже встретится честно нелинейная формула — добавим `kind: "expression"` с мини-выражением, но начинать с этого не нужно.

## 4. Стандартный профиль OBD-II в этом же формате

```json
{
  "schemaVersion": 1,
  "id": "obd2-standard",
  "name": "OBD-II (SAE J1979)",
  "priority": 0,
  "match": {},
  "bus": { "elmProtocol": "0" },
  "ecus": [
    {
      "id": "broadcast",
      "name": "Эмиссионные ECU",
      "addressing": { "request": "7DF" },
      "session": { "kind": "none" },
      "dtc": {
        "read":        { "request": "03", "format": "j1979" },
        "pending":     { "request": "07", "format": "j1979" },
        "permanent":   { "request": "0A", "format": "j1979" },
        "clear":       { "request": "04" },
        "freezeFrame": { "request": "02{pid}{frame}", "format": "j1979FreezeFrame" }
      },
      "supportedParametersProbe": "j1979Bitmap",
      "parameters": [
        {
          "id": "std.rpm", "name": "Обороты двигателя",
          "request": "010C", "responsePrefix": "410C",
          "extract": { "start": 0, "length": 2 },
          "decode": { "kind": "linear", "scale": 0.25, "offset": 0 },
          "unit": "rpm", "group": "live-fast", "categories": ["hud"]
        },
        {
          "id": "std.coolant", "name": "Температура ОЖ",
          "request": "0105", "responsePrefix": "4105",
          "extract": { "start": 0, "length": 1 },
          "decode": { "kind": "linear", "scale": 1, "offset": -40 },
          "unit": "°C", "group": "live-slow", "categories": ["hud"]
        }
        /* … остальные mode-01 PID переносим из таблицы J1979 — это разовая работа */
      ]
    }
  ]
}
```

Отличия от производительского профиля — только в данных: functional-адресация, нет сессии, DTC формата J1979, freeze frame через mode 02 с плейсхолдерами `{pid}` и `{frame}` (номер кадра, по умолчанию `00` — единственный кадр по стандарту J1979). Запрос freeze frame движок адресует тому ECU, который сообщил код.

### Как движок узнаёт, что поддерживается

- **J1979:** `supportedParametersProbe: "j1979Bitmap"` — движок один раз опрашивает битмаски `0100/0120/…` и отфильтровывает список.
- **UDS:** пробуем DID; отрицательный ответ `7F 22 31` (requestOutOfRange) = параметр не поддерживается — выкидываем и кэшируем результат per-VIN, чтобы не пробовать каждый раз.

## 5. Пример: реальный производительский профиль (VAG MQB, бензин)

```json
{
  "schemaVersion": 1,
  "id": "vag-mqb-petrol",
  "name": "VW Group MQB — бензин",
  "priority": 100,
  "match": { "brands": ["volkswagen", "skoda", "seat", "audi"], "vinWMI": ["WVW", "WVG", "TMB", "VSS", "WAU"] },
  "bus": { "elmProtocol": "6" },
  "ecus": [
    {
      "id": "engine",
      "name": "Двигатель",
      "addressing": { "request": "7E0", "response": "7E8" },
      "session": { "kind": "uds", "open": ["1003"], "testerPresent": { "request": "3E80", "intervalSec": 2 } },
      "dtc": {
        "read":        { "request": "1902AF", "format": "uds" },
        "freezeFrame": { "request": "1904{dtc}FF", "format": "udsSnapshot" }
      },
      "parameters": [
        {
          "id": "vag.vin", "name": "VIN",
          "request": "22F190", "responsePrefix": "62F190",
          "extract": { "start": 0, "length": 17 },
          "decode": { "kind": "ascii" }, "group": "once", "categories": ["info"]
        },
        {
          "id": "vag.rpm", "name": "Обороты",
          "request": "22F40C", "responsePrefix": "62F40C",
          "extract": { "start": 0, "length": 2 },
          "decode": { "kind": "linear", "scale": 0.25, "offset": 0 },
          "unit": "rpm", "group": "live-fast", "categories": ["hud"]
        }
        /* Проприетарные DID (температура масла, наддув, DSG и т.д.) —
           это ровно то, что команда собирает по семействам ECU.
           Каждая находка = ещё один объект в этом массиве. */
      ]
    }
  ]
}
```

Полезный факт: диапазон DID `F400–F4FF` стандартизован в ISO 14229 как зеркало J1979-PID (F40C = RPM, F405 = температура ОЖ), `F190` = VIN — это работает на большинстве UDS-ECU и даёт «бесплатный» стартовый набор для любого производительского профиля ещё до сбора проприетарных DID.

## 6. Что делает движок (интерпретатор профиля)

```
ProfileStore   — читает *.json из бандла (позже с сервера), валидирует schemaVersion
ProfileMatcher — по данным авто из Garage/VIN выбирает профили (стандартный + лучший производительский)
ELM327Session  — транспорт + init адаптера + очередь команд (наследие легаси, переписанное на Swift)
ECUChannel     — применяет addressing/session конкретного ECU, держит tester present
Scheduler      — крутит группы опроса (live-fast/live-slow/once), дедуплицирует запросы,
                 использует подсказку числа ответов («010C 1») для скорости
Decoder        — чистая функция: (байты ответа + описание параметра) → значение
DTCReader      — исполняет dtc.read/pending/permanent/clear/clearSingle, парсит j1979/uds форматы
FreezeFrameReader — mode 02 или 19 04, расшифровка через ту же таблицу параметров
```

Предлагаемое наполнение группы `Classes/OBD`:

```
OBD/
├── Transport/        # BLETransport (CoreBluetooth); позже WiFiTransport (тот же интерфейс поверх TCP)
├── Adapter/          # ELM327Session: init-последовательность, очередь, таймауты, особенности клонов
├── Codec/            # J1979 / UDS / ISO-TP-строки: сборка запросов, разбор ответов, NRC
├── Profile/
│   ├── Model/        # Codable-модели схемы из этого документа
│   ├── Store/        # загрузка и валидация
│   ├── Matcher/      # подбор по авто
│   └── Resources/    # obd2-standard.json, vag-mqb-petrol.json, ...
├── Engine/           # ECUChannel, Scheduler, Decoder, кэш поддержки параметров
└── Features/         # LiveDataService (HUD), DTCService, FreezeFrameService
```

Wi-Fi-адаптеры позже добавляются заменой одного слоя: это TCP-сокет (обычно 192.168.0.10:35000) с тем же текстовым ELM-протоколом поверх.

## 7. Процесс наполнения профилей (работа команды)

Профиль «собран», когда по семейству ECU известны: пары CAN ID (для VAG уже есть — vag-uds-ids), нужна ли `10 03`, и таблица DID → байты → формула → единицы. Источники: находки команды (python-скрипты — переносить содержимое запросов в `parameters` 1:1), community-базы (VCDS label-файлы, Car Scanner/Torque custom PID базы, awesome-automotive-can-id), проверка на живых машинах. PDF «Coverage» задаёт порядок: начать с VAG MQB (лучше всего задокументирован), затем Toyota/Hyundai-Kia.
